# Design: 数据可移植性（本地导入导出 + 对象存储备份）

Generated by /office-hours on 2026-06-17
Branch: feature/0.1.3.4
Repo: octane
Status: APPROVED
Mode: Builder

> 本设计由 `/office-hours` 产出。UI/UX 部分结合 `ui-ux-pro-max` 检索结果与项目现有 Semi UI 体系。
> 关键决策已与作者敲定：D1:A（密文导出）+ D2:B（AK/SK 经主密码加密存储）+ D3:A（手动上传/下载），diff/合并不做。

## Problem Statement

octane 当前所有数据（workspace / category / bookmark / context / 加密元数据）仅存于本地 IndexedDB，没有备份、迁移、跨设备同步能力。换设备、重装扩展、清理浏览器数据都会导致**全部书签与上下文永久丢失**。本设计为 octane 增加「数据可移植性」：本地全量导入导出 + 阿里云 OSS / 腾讯云 COS 手动备份恢复，均为覆盖式。

## What Makes This Cool

加密数据的迁移天然安全且零额外成本。octane 的密钥由「用户密码 + salt」派生，**派生密钥从不落盘**（只存 `chrome.storage.session`，重启清空），落盘的只有 `cryptoMetadata`（含 salt）与密文。因此：导出文件里既没有密钥、也没有明文，但只要导入方使用**同一个主密码**，即可重新派生出同一密钥、完整解密。加密内容不需要任何特殊处理，照搬密文即可迁移。

## Constraints

- **无后端**：纯浏览器扩展，对象存储只能走 AK/SK 直传签名（STS 临时凭证需自建后端，超范围，不做）。
- **加密约束**：派生密钥仅存 session，覆盖式导入含加密数据时，导入方必须用导出端的密码解锁。
- **技术栈固定**：WXT + React 18 + @douyinfe/semi-ui + Zustand + TypeScript + Vitest。UI 必须与现有 Semi UI 界面一致。
- **数据范围**：IndexedDB `octane-db` v2 共 5 张表（`workspaces` / `categories` / `bookmarks` / `contexts` / `cryptoMetadata`），是导出全集，无遗漏用户数据。

## Premises

1. **加密数据可密文迁移**（前提）。证明链路：导出端 `cryptoMetadata.salt` + contexts 密文 → 导入端写入同 salt → 用户输同密码 → `deriveKey(password, salt)` 得同密钥 → 解密成功。覆盖式导入下，本机原数据被全替换，不存在新旧 salt 冲突。**导入后必须 `lock()` 清 session 旧密钥**（salt 已变，旧密钥与新数据不匹配），再以导出端密码重新解锁。
2. **导入为覆盖式**（先清空 5 表再写入），不做 diff/合并。理由见下「diff/合并评估」。
3. **对象存储走 AK/SK 直传**，STS 需后端超范围。
4. **AK/SK 经主密码 AES-GCM 加密后存 `chrome.storage.local`**（复用现有加密基建），配置/使用云前需先解锁主密码。
5. **手动触发上传/下载**，不引入定时器与冲突仲裁状态机。

## diff / 合并评估（决定不做）

技术上可行，但难度与风险集中在三处，性价比低：

- **冲突仲裁**：明文记录可按 `id` + `updatedAt` 取胜，但 `bookmarks` 冗余字段（`contextCount`/`hasEncryptedContext`）需合并后重算，否则 UI 错乱。
- **引用完整性**：合并后必须校验 `category.workspaceId` / `bookmark.categoryId` / `context.bookmarkId` 全部指向存在的父记录，否则出现孤儿数据破坏现有级联逻辑（`database.ts:120-187`）。
- **加密记录合并陷阱**：两端密码相同（同 salt）时密文可按 id+updatedAt 仲裁；密码不同时密文完全无法跨端合并，「加密记录该归谁」语义暧昧。

**结论**：本版只做覆盖式。diff/合并记为 backlog，待真有多设备并发编辑诉求时单独设计。

## Approaches Considered

### 决策 D1 — 加密数据导出形态
- A) 密文导出（默认）：导出 `encryptedData`/`iv`/`cryptoMetadata`，文件无明文无密钥。✅ 选定
- B) 密文 + 可选明文导出（需先解锁）：多一个便利出口，但引入明文泄露面。
- C) 只导出非加密数据：丢弃加密笔记，不可接受。

### 决策 D2 — 对象存储凭证存储 ⚠️ 安全决策
- A) AK/SK 明文存 `chrome.storage.local`：最简单，但密钥裸落盘。
- B) AK/SK 经主密码 AES-GCM 加密后存 `chrome.storage.local`：复用现有加密基建，凭证不以明文落盘。✅ 选定
- C) 自建后端签 STS：超范围，劝退用户。

### 决策 D3 — 云同步深度
- A) 手动上传/下载（备份/恢复），覆盖式。✅ 选定
- B) 加自动定时同步：引入定时器与「最后写入覆盖」问题。
- C) B + 增量同步：等同 diff/合并，不做。

## Recommended Approach

**D1:A + D2:B + D3:A**。落地为：本地全量导入导出（JSON，覆盖式）+ 对象存储手动备份恢复（OSS/COS，凭证经主密码加密存储），加密数据全程密文迁移，零明文落盘。

## 技术方案

### 1. 导出格式（JSON Schema）

```jsonc
// octane-backup-YYYYMMDD-HHmmss.json
{
  "schema": "octane-backup",
  "version": 1,                       // 备份格式版本，未来 schema 变更时递增
  "exportedAt": 1718600000000,        // 毫秒时间戳
  "appVersion": "0.1.3.4",            // 取构建时 octane 版本（读 VERSION/package.json），勿硬编码
  "data": {
    "workspaces":   [ /* Workspace[] 原样 */ ],
    "categories":   [ /* Category[] 原样 */ ],
    "bookmarks":    [ /* Bookmark[] 原样（含冗余字段 contextCount/hasEncryptedContext） */ ],
    "contexts":     [ /* Context[] 存储态原样：
                         非加密：含明文 content，无 encryptedData/iv
                         加密：content 为 ''，含 encryptedData/iv 密文 */ ],
    "cryptoMetadata": { /* 单例，含 salt/iterations/algorithm。含加密数据时必导 */ }
  }
}
```

要点：
- contexts 直接取 `getAll('contexts')` 存储态序列化，**不解密、不补明文**（`ContextService.ts:8-20` 的 `getContexts` 会解密，导出不能用它；必须用底层的 `getAll`）。
- 非加密 context 的 `content` 是持久化明文（`ContextService.ts:62-73`），原样导出。
- 加密 context 的 `content` 存储时已是 `''`（`ContextService.ts:53`），导出的就是空，无明文泄露。

### 2. 导出流程

```
点击「导出」
 → 收集 5 张表 getAll
 → 组装 { schema, version, exportedAt, appVersion, data }
 → JSON.stringify → Blob → 触发下载 octane-backup-<ts>.json
 → Toast.success（绝静默成功，ui-ux-pro-max: Confirmation Messages）
```

无破坏性，无需二次确认。仅一个轻提示「备份文件含加密笔记，恢复时需用相同主密码」。

### 3. 导入流程（覆盖式，单事务原子，background 执行）

**执行上下文（必须 background）**：导入/恢复在 **background service worker** 执行。popup 是瞬态容器（`navigation.ts:1-3`），用户关闭即销毁，长事务与网络请求会被中断。popup 只负责选文件 + 强确认，事务本身通过 WXT messaging（`browser.runtime.sendMessage` ↔ background `onMessage`）交给 background，结果回传 popup 显示。

复用现有事务范式（`database.ts:120-149` 的 `cascadeDeleteWorkspace`），跨表单事务：

```
popup 选文件 → 解析 + 校验（见下）
 → 强确认 Modal（破坏性，二次确认，见 UI 节）
 → 消息发往 background 执行覆盖事务：
   tx = db.transaction(['workspaces','categories','bookmarks','contexts','cryptoMetadata'], 'readwrite')
   // 4 张数据表：清空 + 写入
   workspaces/categories/bookmarks/contexts → clear() → 逐条 put(record)
   // cryptoMetadata 仅在备份包含时写入（C1 边界：不含则保留本机原值）
   if 备份含 data.cryptoMetadata → put('singleton', 备份值)
   await tx.done
   // 重算冗余字段（C5：防备份被篡改导致解锁 gate 错乱）
   遍历导入的 bookmarks → syncContextMeta(bookmarkId)
   // 清 session 旧密钥（C2：salt 已变，旧密钥与新数据不匹配）
   lock()
 → 显式广播刷新（见下）
 → Toast.success + 提示「如含加密数据，请用导出端主密码重新解锁」
```

**广播刷新（关键纠正，修复与代码事实的不一致）**：底层 `db.transaction` + `objectStore.put` 绕过了 `putRecord`，**不会触发任何 broadcast**；且现有监听只在 `store==='bookmarks'` 时刷新当前 hostname（`useHostBookmarks.ts:53-56`），**不存在「全量刷新」机制**。因此导入事务结束后必须显式处理：
- 对 `workspaces`/`categories`/`bookmarks`/`contexts` 四张表各显式调一次 `broadcast(store, 'put')`（复用 `database.ts:24`）；
- sidepanel：现有 `useHostBookmarks`（`useHostBookmarks.ts:53-56`）在收到 `store==='bookmarks'` 广播后重新匹配当前 hostname，导入后对 bookmarks 表显式广播即可让其刷新。
- newtab：**经核实 `src/entrypoints/newtab/` 及其 store（`useWorkspace`/`useBookmarks`）当前未订阅任何 BroadcastChannel**——全仓库仅 sidepanel 的 `useHostBookmarks` 消费广播。故显式广播对 newtab 无效。**必须新增一个 `'import'` 全量事件，并在 newtab 入口订阅该事件触发 `loadWorkspaces` + `loadBookmarks` 整体 reload**；否则导入后 newtab 不刷新、数据不一致。这是已确认必须做的实现项，非待定项。

**校验（解析阶段，写入前）**：
- **文件大小阈值检查（C4）**：超阈值（如 50MB）直接拒绝，避免 `JSON.parse` 卡死或内存溢出。
- `schema === 'octane-backup'`；**`version` 必须是已知版本——本版仅接受 `version=1`（CL2 版本策略）**。更高版本拒绝并提示「备份版本过高，请升级 octane」；未来 schema 变更递增 version 并写迁移逻辑。
- `data` 为对象；`workspaces`/`categories`/`bookmarks`/`contexts` 为数组、`cryptoMetadata` 为对象（若存在）。
- **字段级校验（C5）**：context 必含 `id`/`bookmarkId`；bookmark 必含 `id`/`workspaceId`/`categoryId`。引用完整性事务后顺带校验，并对受影响 bookmark 重算冗余字段。
- 若 `data.contexts` 含 `isEncrypted=true` 但 `data.cryptoMetadata` 缺失 → 拒绝并提示「备份含加密数据但缺少加密元数据，无法恢复」。
- 校验失败一律不进入确认流程，红色错误 + 恢复路径文案（ui-ux-pro-max: Error Recovery）。

**原子性**：单 `readwrite` 事务，任一步失败整体回滚，不会出现「清空了但没写完」的半成品状态。

### 4. 加密数据迁移说明

导入写入 `cryptoMetadata`（含导出端 salt）后，本机派生密钥的 salt 变为导出端值。用户随后用**导出端密码**解锁（`unlock(password)` → `deriveKey(password, 导入的 salt)` → 同密钥 → 解密成功）。覆盖式下本机原数据已被替换，不存在「原加密笔记 salt 不匹配」。

**关键约束**：导入后若用户用错密码，解密失败但不泄露明文（现有 `useEncryptedContexts` 的 error 状态已处理，`useEncryptedContexts.ts:58-66`）。UI 需明确告知「请使用导出此备份时的主密码」。

### 5. 对象存储（OSS / COS）

#### 5.1 凭证加密存储（D2:B）

新增 `CloudStorageService`，凭证不入 IndexedDB，入 `chrome.storage.local`：

```
配置保存：
  plaintextCreds = { provider, region, bucket, accessKeyId, accessKeySecret, [endpoint] }
  要求已解锁主密码（getEffectiveKey() 非空）
  { ciphertext, iv } = encrypt(JSON.stringify(plaintextCreds))   // 复用 CryptoService.encrypt
  chrome.storage.local.set({ 'octane.cloudCreds': { ciphertext, iv, savedAt } })

使用（签名直传）：
  要求已解锁
  raw = decrypt(ciphertext, iv)
  creds = JSON.parse(raw)
  用 creds 调用 OSS/COS SDK 直传
```

由于凭证被主密码加密，**配置云存储与每次上传/下载前都必须处于已解锁状态**。解锁态在 `chrome.storage.session` 生命周期内复用（service worker 重启**不**清空 session，仅浏览器完全关闭才清空，故浏览器会话期间不必重复输密码）；仅当 session 密钥被清时才需重新解锁（触发一次 PBKDF2 600k 迭代，百毫秒级）。UI 在未解锁时禁用云操作并提示解锁（见 UI 节）。

补充：AES-GCM 的 `iv` 非秘密，可与密文一同明文存于 `chrome.storage.local`，**无需对 iv 加密**。

#### 5.2 OSS / COS 选型与签名

- **推荐用官方 SDK**：`ali-oss`（浏览器构建）+ `cos-js-sdk-v5`。两者都支持浏览器环境，内部封装签名，避免手写 HMAC-SHA1/V5 签名的易错实现。
- **待验证（列为 P2 验证项）**：两个 SDK 在扩展 service worker（WXT background）或 popup 文档上下文下的可用性与打包体积；若体积过大或兼容性问题，回退到手写签名（OSS V1 用 SubtleCrypto HMAC-SHA1，COS V5 多层 HMAC-SHA1）。
- **备份对象**：固定 key，如 `octane/backup/octane-backup.json`（单文件覆盖，对应覆盖式语义）。不做多版本/历史。

#### 5.3 上传 / 下载（手动，D3:A）

```
上传备份：
  creds 解密 → 本地导出生成 JSON（同导出流程） → SDK.put(backup.json, blob) → 记录 lastBackupAt
  进度态 → 成功 Toast（含时间）/ 失败 Toast（含错误 + 重试）

从云恢复：
  creds 解密 → SDK.get(backup.json) → 走「导入流程」（同校验 + 强确认 + 覆盖事务）
  上次备份时间 + 恢复是破坏性操作，需二次确认
```

#### 5.4 部署侧前置条件（文档需告知用户）

- **桶 CORS**：OSS/COS 桶必须配置 CORS 允许扩展 origin（`chrome-extension://<id>` / `moz-extension://<id>`，或 `*` 调试期）放行 GET/PUT/HEAD。
- **WXT host_permissions**：`wxt.config.ts` 需为 OSS/COS 域名加 host 权限（`https://*.aliyuncs.com`、`https://*.myqcloud.com`）。
- **最小权限 AK/SK**：建议用户为该备份单独建子账号，仅授权目标 bucket 的读写，降低 AK/SK 泄露影响面。
- **CORS 通达性优先验证（硬前置）**：CORS 是云功能能否工作的硬门槛。P2 启动后第一件事用最小 PUT 请求验证扩展 origin 可达，再集成 SDK——避免 SDK 接完才发现 CORS 拦截。

### 1. 入口架构：扩展 SettingsView

设置页用 `SubPageHeader`（标题「设置」+ 返回）+ 内容区，内容区纵向两段：**本地备份** + **云备份**。

### 3. 关键交互状态机（来自 ui-ux-pro-max: Confirmation Dialogs / Submit Feedback / Loading States）

**导入（本地文件 / 从云恢复）— 破坏性，强确认**：
```
选文件 → 解析校验
  失败 → Modal(error): 红框 + 错误文案 + 「检查文件是否为 octane 备份」(Error Recovery)
  成功 → Modal(警告级确认, type=warning):
         标题「确认覆盖全部数据」
         正文：将清除当前 N 个工作区、M 条书签并替换为备份内容，不可撤销。
              [如含加密数据] 恢复后需用导出端主密码解锁。
         主按钮「确认覆盖」(danger) 默认禁用，需勾选 Checkbox「我了解此操作不可撤销」后启用
         点击 → 进度态（Spin + 「正在导入…」）→ success Toast / error Toast(含重试)
```

**导出 / 上传备份 — 非破坏性**：
```
点击 → Spin 按钮内 loading（loading-buttons：async 期间禁用按钮）→ success Toast(含时间)
     失败 → error Toast + 错误信息（含「重试」）
```

**云连接测试**：
```
填配置 → [测试连接] → Spin → success Toast「连接成功，桶可访问」/ error「连接失败：<原因，如 CORS/权限>」
错误信息需可操作：提示检查桶 CORS 与 AK/SK 权限（Error Recovery）。
```

**状态汇总**（Zustand `useBackup`）：每操作四态 `idle | running | success | error`，`running` 时对应按钮 loading + 禁用其他操作防并发。错误一律 `role="alert"` / aria-live 播报（ui-ux-pro-max: Error Messages 必须可访问）。

### 4. Semi UI 组件选型

| 用途 | 组件 |
|---|---|
| 两段容器 | `Card`（title/spacing，与现有界面一致） |
| OSS/COS 切换 | `Tabs` |
| 凭证输入 | `Input`（AccessKeySecret 用 `mode="password"`）+ 必有 `label`（**禁止 placeholder-only**，ui-ux-pro-max: Form Labels） |
| 区域选择 | `Select` |
| 主操作 | `Button`（导出/上传 primary；导入/恢复 `type="danger"`；async 时 `loading`） |
| 覆盖确认 | `Modal`（`type="warning"`，配合 Checkbox 二次确认） |
| 轻提示 | `Toast`（success/error，绝静默） |
| 常驻说明/警告 | `Banner`（info=含密文说明；warning=未解锁；error=配置错误） |
| 进度 | `Spin`（操作 >300ms 即反馈，ui-ux-pro-max: Loading Indicators） |

受控组件（`value`+`onChange`，ui-ux-pro-max: Controlled components），状态进 `useBackup`。TypeScript 给 `useState` 显式类型。

### 5. 安全提示文案（信任导向）

- 本地备份区 Banner(info)：「导出文件包含加密笔记的**密文**（非明文）。在另一台设备恢复时，请使用**相同的主密码**解锁。」
- 云备份区未解锁 Banner(warning)：「云备份凭证由你的主密码加密存储，使用前请先解锁。」
- 配置区脚注：「AccessKeySecret 经主密码 AES-GCM 加密后存储于本机，不会明文保存。建议使用仅授权本桶读写的子账号密钥。」
- 导入/恢复确认 Modal：「此操作将**清除并替换**当前全部数据，不可撤销。」

### 6. 视觉处理原则

- 破坏性操作（导入覆盖、从云恢复）：`Button type="danger"` + Modal 警告级 + Checkbox 二次确认，三重门槛。
- 普通操作（导出、上传、测试连接）：克制，primary/borderless，loading 内联。
- 全程不引入新配色、新字体，沿用 Semi UI 默认主题（亮/暗随系统）。

## Success Criteria

- 本地导出生成的 JSON 经本地导入后，5 表数据逐字段一致（含加密 context 可用原密码解锁）。
- 导入是原子事务：模拟中途失败，数据库回到导入前状态，无半成品。
- 云配置保存后 AK/SK 在 `chrome.storage.local` 中为密文（不可读明文）；清除主密码 / 未解锁时无法获取凭证。
- 上传备份 → 从云恢复 → 数据一致，且加密笔记可解。
- 破坏性操作有三重确认门槛；所有异步操作有 loading + success/error 反馈；错误可访问（aria-live）。
- Vitest 覆盖：`validateBackup`（合法/非法/缺 cryptoMetadata）、导入覆盖事务（成功/回滚）、凭证加解存取、OSS/COS 适配的 mock 单测。
